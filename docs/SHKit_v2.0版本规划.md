## 0. 一句话结论

v2.0 的数学核心只有**一个新算子**：球面水平梯度。

它已经被**数值验证到 2e-10**（对 SHKit 自己已验证的 `synthesis()` 做有限差分），
并且在**点质量载荷**上通过了物理方向检验（24 点环上 `cos(指向载荷)` 均值 **+0.99982**）。
所以水平形变**不是"难做的研究题"，而是一段 ~200 行、有铁律可验的实现**。

真正的工作量分布是：

| 支柱 | 性质 | 占比 |
| --- | --- | --- |
| ① 多时间批量处理 | IO 与流程工程（数学已就绪） | ~40% |
| ② 水平形变 | 一个新算子 + 单位体系扩展 + 验证 | ~20% |
| ③ 结果显示 | 界面工程（对标 m2py 的结果显示） | ~40% |

### 1.2 明确不做（与 `方案调研.md` §9 同风格）

1. 不做**三维形变的反演**（由水平形变反推位系数只到差一个常数，见 §3.8）；
2. ~~不做 FFT 快速路径~~ → **v2.0 改变决定**：新增 **A3 FFT 经度路径**（§2.3）。
   原 `方案调研.md` §5 拒绝 FFT 的两条理由（"正反变换必须配对"的隐式约束、
   区域网格的 Gibbs 振铃）**用"自动选择 + 自动报告 + 可回退 + 硬条件"解决**，
   而不是靠"干脆不做"。**直接法仍是默认与唯一通用路径**，FFT 只是被自动挑中的加速分支；
3. 不做 dask / 延迟加载；不做 DDK 滤波；不做 mascon / Slepian 时变反演；
4. 不做完整统计推断（只给 1σ 与 SNR，不做 AR(1)、Mann-Kendall）；
5. 不做自动剔除/插补可疑历元（只报告）；
6. 不追求与 MATLAB 中间产物逐位相同（只保证能读能写能对上账，差异可解释）；
7. `m2py` 的 `fft↔fft 必须配对` 这类隐式约束**不继承**；`m2py`/`m2csharp` 的
   FFT **收尾索引也不继承**（它整体平移了一个经度格，见 §2.3）。
8. **不做散点的"查表+归约"加速**：SHSynth 实测在随机散点上反而更慢
   （2 万点 0.63 s → 1.12 s，即 0.6×），只在"唯一纬度远少于点数"时略快（1.5×）。
   收益不稳定，不引入。

## 2. 支柱一：多时间批量处理（摘要）

完整的 12 项空白清单、接口草案、P0–P6 分解、性能预算、9 类验证，见
[`多时间数据处理方案.md`](多时间数据处理方案.md)。此处只保留 v2.0 相关的要点。

### 2.1 三个已实测的关键事实

| 事实 | 数字 | 对 v2.0 的影响 |
| --- | --- | --- |
| 读一个历元极快 | 单个 `GSM-*.gfc` 0.003 s；203 个 ≈ 0.5 s | **主路径是"读 gfc 序列"，不是重新做球谐分析**（后者 1° 全球 / nmax=60：一次调用 203 历元 ≈36 s，逐历元循环 ≈543 s；见 §2.3） |
| legacy 十进制年口径 | 反解并验证：**200/203 精确 ≤1e-6**（3 个跨年历元 ≤4.11e-5） | `TimeAxis` 必须按"结束日排他 + 闰年 366"实现，并加反例回归 |
| netCDF4 打不开中文路径 | 本机实测 `D:\华为家庭存储\...nc` **读**→`FileNotFoundError`、**写**→`PermissionError`（误导性强） | **A0.5 必修**（✅ 已修，见 §4.2）；读走临时副本，**写先落 ASCII 临时再 move** |

### 2.2 核心约定（不可妥协的三条）

1. **权重只算一次**：`compute_weights` 与时间无关，N 个历元共享同一套 Voronoi/Delaunay/grid 权重。
2. **不做等间隔假设**：GRACE 月度解间隔 27–35 天，还有整月缺失与一年两解；凡"月"一律用真实时间间隔。
3. **空间滤波与时间滤波物理隔离**：`gaussian_km`（球面空间核）与 `time_window`（时间核）不得共用一个参数名，报告里分别列明且各自"只施加一次"。

### 2.3 ⚡ 批量处理的效率：SHKit 自身实测

> 这一节回答"批量处理还有个效率问题"，数字全部是**本机实测**（Intel Ultra 7 265K，
> 与 SHSynth 方案 §6 同一台机器），基准几何 = 1° 全球 `181×360 = 65 160` 点、
> `nmax=60`、`ntime=24`（真实 CSR 历元量级）。

**① 「一次调用」比「逐历元循环」快一个量级 —— 而且原因不只是 BLAS**

| 调用方式（公开 API `analysis_quadrature`） | 耗时 | 每历元 |
| --- | --- | --- |
| 一次调用 `ntime=24` | **4.21 s** | 0.176 s |
| 逐历元调用 24 次（外推） | 64.2 s | **2.676 s** |
| **每历元惩罚** | | **15.3×** |

外推到用户的 **203 个真实历元**：一次调用 **≈36 s**，逐历元循环 **≈543 s（9 分钟）**。

**② 一次调用内部的时间去哪了（分解实测）**

| 组成 | 耗时 | 占比 | 与时间有关？ |
| --- | --- | --- | --- |
| 投影核心 `_quadrature_C` | 1.113 s | 26% | 是 |
| **`synthesize`（算拟合残差用）** | **1.898 s** | **45%** | 是 |
| `_fill_gram` 诊断 | 0.557 s | 13% | **否 —— 可提到循环外** |
| 其它（`_fill_dc`、检查） | ≈0.64 s | 16% | 否 / 部分 |

⇒ **两个立刻可做的优化**（本质都是"把与时间无关的东西提出去"）：

1. **`_fill_gram` / `_diagonal_completeness` 只依赖 `(lat, lon, w, nmax)`**，与时间无关 →
   批量时必须**只算一次**；否则 N 个历元白算 N 遍，这是逐历元惩罚的重要来源；
2. **`synthesize`-for-fit 占了一次调用的 45%**，而它只为报告 `residual_rms` / `fit_rmse_rel`。
   批量模式应提供 `report_fit=True/False`，并在文档里说清"关掉省 45%，代价是没有逐历元残差表"。

**③ FFT 经度路径：投影核心再快 44×（原型已在 SHKit 上跑通）**

全球等经纬网格上，经度方向的 cos/sin 分解本可用一次 FFT 完成：

```
直接法  : Σ_m (nmax−m+1)·(nlat·nlon)·ntime = O(nSHCS·nlat·nlon·ntime)
FFT 路径: O(nSHCS·nlat·ntime) + O(nlat·ntime·nlon·log nlon)
```

| 项（投影核心，同几何同批量） | 耗时 | 每历元 |
| --- | --- | --- |
| 直接法（`_quadrature_C`） | 1.113 s | 0.049 s |
| **FFT 原型（含勒让德递推）** | **0.027 s** | 0.0011 s |
| FFT 原型（几何复用，勒让德只算一次） | 0.0147 s | 0.0006 s |
| **加速比** | **44×** | |

| 一致性检查（FFT vs 直接法） | 实测 |
| --- | --- |
| 随机场、`nmax=60`、`ntime=24` | `max\|ΔC\| = 2.67e-19`，`max\|ΔS\| = 2.40e-19`（`\|C\|max = 1.9e-5`）→ 机器精度 |
| 纯谐波恢复 `C₇₄=1, S₉₃=1`（**必须含 `m≥1` 正弦项**，这是经度对齐的唯一探针） | 两路都给 `C₇₄=0.999949231203281`、`S₉₃=0.999949231254919`，差 ≤3.6e-16 |
| 含极点行（lat −90..90）与不含极点行（lat −88..88） | 都 ≤3.6e-16 |

外推到 **203 历元**：投影核心 直接 **≈10 s** → FFT **≈0.23 s**。
⇒ **配合同步"提出与时间无关的项"，一次调用有望从 ≈36 s 压到 1~2 s 量级。**

> ⚠️ **FFT 只能作为"自动选择 + 自动报告 + 可回退"的加速路径，不能替代直接法。**
> 硬条件 `nlon > 2·nmax`（否则 `m` 超过 Nyquist 会**混叠** —— 这不是"慢一点"而是"算错"）；
> 适用**整圈、均匀的经度**（全球网格，**以及只取一段纬度的纬向区域** —— FFT 只在经度方向起作用）；
> 经度是区域/非均匀、散点 → 直接法。汇总里必须打印本次走的是哪条路及回退原因。

> ⚠️ **绝不能照抄 m2py / m2csharp 的 FFT 收尾索引。** SHSynth 方案 §6.5.4 已定位：
> 其 `_SH2grid_fft` 用 `fliplr(real(ifft(conj(spectrum))))`——先 `conj` 使经度反序、
> `fliplr` 翻回来却**留下一个 +1 格的平移**（相对误差 2.7e-01；平移 −1 格后降到 8.7e-14）。
> 只看全球统计量**永远发现不了**这个错。SHKit 必须用朴素 `rfft/irfft`，
> 回归测试必须用 **`m≥1` 的系数**钉住经度对齐。

### 2.4 与 SHSynth 的冻结契约（跨包互操作）

SHKit（分析）与 SHSynth（综合）是同作者的两个独立包，**靠文件互操作，不靠 import**。
SHSynth 方案 §12 已把两侧共用的落盘契约**冻结**，SHKit v2.0 必须逐字对齐：

| 项 | 约定（以 SHSynth 方案 §12.1 为准） |
| --- | --- |
| 维度 | `time = N`，`n = L+1`，`m = L+1` |
| 系数变量 | `c(time,n,m)`、`s(time,n,m)`（float64；**读时也接受 `C`/`S`**） |
| 时间坐标 | `time(time)` `datetime64[ns]`；读时也接受 `int32 + units="days since …"` |
| 阶次坐标 | `n(n)`、`m(m)` 整数；缺失时按稠密方阵推 |
| 全局属性 | `norm="4pi"`、`csphase=1`、`field_unit`、`nmax`、`gaussian_km`、`tide_system`、`center`、`mission`、`product`、`rl`、`source_files`、`time_source`、`coverage_start`、`coverage_end`、`created`、`producer` |
| 宽容读 | 维度顺序、变量大小写、坐标缺失、时间缺失（降级为序号 + 警告） |
| 三角互操作 | `*.dat`：首行 = 历元编号表头，主体 `(2*NC, ntime)`；`*_TimeInfo.dat`：`[idx, y_start, y_end, y_mid]`（口径见 §2.1） |
| 水平形变场序列 | 一个文件装 `north_displacement` / `east_displacement`（可选 `magnitude`/`azimuth`），共享 `lat/lon/time`；**不写 `standard_name`**（CF 无对应标准名，宁可不写也不编） |

⇒ SHKit 侧动作：`write_coeffs(layout='series_nc')` 按上表实现；契约双方开工后**冻结**，改动要同步两个包。

### 2.5 水平形变的冻结契约（已定：**两边各自实现**）

**决策**：水平形变在 SHKit 与 SHSynth 里**各写一份**，不共享代码、不互相 import
（两个包必须能各自独立安装运行）。因此**唯一的保障是冻结约定 + 逐位对表**。

#### 2.5.1 必须冻结的 11 项（任何一项不一致，两边就对不上）

| # | 项 | 冻结值 |
| --- | --- | --- |
| F1 | 归一化与相位 | 4π 归一化、**无 Condon–Shortley 相位**（`norm="4pi"`, `csphase=1`） |
| F2 | 逐阶因子 | `F^h_n = R·l′_n/(1+k′_n)`，`R = 6378136.46 m`（`EARTH_RADIUS_M`），勒夫数表 = **PREM-LLN / Wang et al. 2012**（`love_numbers="PREM/Wang2012 (load l')"`） |
| F3 | 符号约定 | `θ̂` 指**南**、`λ̂` 指**东**；`u_N = −∂S/∂θ`，`u_E = +(1/sinθ)·∂S/∂λ` |
| F4 | 极点 | **精确值，不是 ε 极限**：`P̄_n1/sinθ → Q_n1(±1)`（`Q_11=√3`），`m≥2 → 恰为 0`；`dP̄/dθ` 由递推求导给出，不特判 |
| F5 | `m=0` 规则 | `m=0` 只对 `u_N` 有贡献，对 `u_E` 恒为 0（**漏掉会让 `u_N` 系统性出错**） |
| F6 | 派生量 | `magnitude = hypot(u_N, u_E)`（极点同样有效）；`azimuth = atan2(u_E, u_N)` 归一到 `[0,360)`、自北顺时针 |
| F7 | 字段名 | `north_displacement`、`east_displacement`、可选 `magnitude`、`azimuth`（**不是** `un`/`ue`/`north`/`east`） |
| F8 | 单位 | `units = "m"`（`--scale mm` 时只改数值与 `units` 字符串，**不改 `field_unit`**）；**不写 `standard_name`** |
| F9 | `field_unit` | `"horizontal_displacement"`（**一个矢量量**，不拆成 east/north 两个量） |
| F10 | 平滑 | `gaussian_km` 是**唯一**的平滑参数，与径向共用，**只施加在系数上、只一次**。<br>⚠️ **不是"可交换"**：球面上 $\nabla_H$ 把阶 $\ell$ 混到 $\ell\pm1$，与逐阶 $W_\ell$ 不交换（实测两种顺序差 $u_N$ **24%**）。所以 `synthesis_horizontal` **故意不接受 `gaussian_km`**，从接口上杜绝二次施加 |
| F11 | 不可逆 | 由水平形变反推位系数**只到差一个常数**（`C00` 不可恢复）→ 两边都必须**拒绝**把它当输入，报错文案都点明 `C00` |

#### 2.5.2 对表机制：**黄金样本（golden fixture）**，不依赖对方安装

两边各自实现，就必须有一种**不装对方也能验证**的对表方式。做法：

1. **冻结一份黄金样本** `tests/fixtures/horizontal_golden.npz`（两个包各存一份**逐位相同**的副本）：

   | 内容 | 说明 |
   | --- | --- |
   | `lat`, `lon` | 一组固定采样点，**必须含 ±90° 两行**与 `lon=90°`（`Q_11` 的探针点） |
   | `C`, `S` | 四组系数：①纯 `C_10` ②纯 `C_11` ③随机带限（`nmax=20`，固定 seed）④真实 GRACE gfc 截断（`nmax=20`） |
   | `u_N`, `u_E`, `magnitude`, `azimuth` | 由**SHKit 侧**算出并冻结的期望值（float64，`np.savez`） |
   | `provenance` | 生成脚本、版本、勒夫数表哈希、日期 |

2. **两边各跑一条独立测试**：`SHKit/tests/test_horizontal_golden.py`、
   `SHSynth/tests/test_horizontal_golden.py` —— 读同一份 fixture，断言自家实现与冻结值一致。
   判据：**`≤1e-12`，目标是 `0.0`**（与既有 `test_vs_shkit.py` 对 `synthesize` 的
   "最大差 `0.0`"同口径）。

3. **可选的对装测试**（对方在场时）：`SHKit/tests/test_vs_shsynth.py`、
   `SHSynth/tests/test_vs_shkit.py`（扩展现有文件）直接互相调用，断言 `≤1e-12`。
   **对方不在时必须优雅 skip 并打印原因**，绝不能让 `run_all.py` 变红。

4. **勒夫数表哈希进 fixture**：F2 的 `F^h_n` 若两边取的 `l′` 表不同（例如一方做了
   CE→CF 改正、另一方没做），水平形变会整体偏几个百分点而**所有内部测试仍然全绿**。
   所以 fixture 里存 `n=1..96` 的 `F^h_n` 向量并单独断言。

#### 2.5.3 冻结的时机与代价

- **时机**：A3 与 SHSynth 的对应阶段**开工前**冻结 F1–F11 + 生成 golden fixture；
  一旦冻结，任一侧改动都要**同步改两个包 + 重新生成 fixture**（fixture 里的 `provenance` 记版本）。
- **代价**：重复实现约 9–14 人日（SHKit 侧，见 §3.12），SHSynth 侧另计；
  换来的是两包各自独立可发布、无 import 依赖 —— 与既有 `synthesize` 的处理方式一致。
- **已知风险**：两边**同时**在"没对表"的状态下各自改公式，会产生"两个都错但错得不一样"的局面。
  → 因此 golden fixture 必须在**任一侧第一次实现时**就生成并冻结，而不是等两边都写完再对。

## 3. 支柱二：水平形变（v2.0 新增）

### 3.1 为什么它不能靠"逐阶因子"混过去

SHKit 已有径向形变 `u_r = C_nm × f_u`，`f_u = R·h′ₙ/(1+k′ₙ)`（逐阶常数）。
**水平形变不是这种形式**：它是同一个标量的**球面梯度**，因此把 (n,m) 耦合到 (n±1,m)：

```
u_r  :  系数 × 逐阶因子                →  同一组 (n,m)
u_N  :  系数 × 逐阶因子 × ∂/∂θ         →  (n,m) 与 (n-1,m) 混合   ← 新的
u_E  :  系数 × 逐阶因子 × (1/sinθ)∂/∂λ →  (n,m) 与 (n,m±1) 混合   ← 新的
```

这正是 `README.md` 里写的"尚未实现的是水平/三维形变——它需要球面水平梯度算子"。

### 3.2 公式（与 SHKit 现有约定一致）

记号：$\bar P_{nm}$ 为 **4π 归一化、无 Condon–Shortley 相位**（等同 SHTOOLS `norm=1, csphase=1`）；
$\mu=\sin\varphi=\cos\theta$，$\theta$ 为余纬；$\hat\theta$ 指向**南**，$\hat\lambda$ 指向**东**。

对标量场 $f=\sum_{n,m}\bar P_{nm}(\cos\theta)\,[C_{nm}\cos m\lambda+S_{nm}\sin m\lambda]$：

$$\frac{\partial f}{\partial\theta}=\sum_{n,m}\frac{\mathrm d\bar P_{nm}}{\mathrm d\theta}\,[C_{nm}\cos m\lambda+S_{nm}\sin m\lambda]$$

$$\frac{1}{\sin\theta}\frac{\partial f}{\partial\lambda}=\sum_{n,m}\frac{m\bar P_{nm}}{\sin\theta}\,[-C_{nm}\sin m\lambda+S_{nm}\cos m\lambda]$$

载荷引起的三维位移（$l'_n$ 为**水平**载荷勒夫数，SHKit 随包已有）：

$$\boxed{\;u_N=\sum_n \frac{R\,l'_n}{1+k'_n}\sum_m \frac{\mathrm d\bar P_{nm}}{\mathrm d\theta}\big[C_{nm}\cos m\lambda+S_{nm}\sin m\lambda\big]\;}$$

$$\boxed{\;u_E=\sum_n \frac{R\,l'_n}{1+k'_n}\sum_m \frac{m\bar P_{nm}}{\sin\theta}\big[-C_{nm}\sin m\lambda+S_{nm}\cos m\lambda\big]\;}$$

（$u_N$ 的符号来自 $\hat\theta$ 指南；实现里等价于 `u_N = -dθ`。）

### 3.3 ✅ 已实测：θ 方向导数递推（这是唯一有坑的地方）

我用 SHKit **自己的** `legendre_pbar()` 对候选递推做了数值验证。结论：

```
sinθ · dP̄_nm/dθ  =  n·cosθ·P̄_nm  −  √((2n+1)/(2n−1)) · √((n−m)(n+m)) · P̄_{n−1,m}
```

| 候选形式 | 相对误差（vs Richardsons 外推的数值导数） | 结论 |
| --- | --- | --- |
| **本文采用（n−1 耦合）** | **1.99e-10** | ✅ 采用 |
| 常见的 m±1 形式<br>`½[√((n+m)(n−m+1))P̄_{n,m−1} − √((n−m)(n+m+1))P̄_{n,m+1}]` | 2.93e-01 | ❌ 直接套用**错**：4π 归一化的 ε_m 在低阶有额外 √2。实测拟合系数 = 教科书值 × `1/√2`(m=1) / `1/2`(m≥2)（配 P̄_{n,m−1} 项），× `1/√2`(m=0) / `1/2`(m≥1)（配 P̄_{n,m+1} 项） |

> ⚠️ **写进代码注释的一条**：网上流传的"m±1 导数递推"是给 **Schmidt 半归一化/含 CS 相位**的，
> 直接拿到 SHKit 的 4π 约定上会错到 30%。要么用 n−1 形式（本方案），
> 要么用 m±1 形式但把 m∈{0,1} 的 ε_m 特殊处理并加回归测试。

**东分量没有递推坑**：$m\bar P_{nm}/\sin\theta$ 直接算，与 $\partial/\partial\lambda$ 的 $\pm$ 配对即可（实测 6.45e-10）。

### 3.4 ✅ 已实测：端到端梯度验证（铁律）

**验证策略是"基无关"的**：不要用另一个递推去验证递推，而是用**已经验证过的 `synthesis()`** 做有限差分：

```
Ψ(lat, lon) = synthesis(lat, lon, coeffs)          # 已有的、已验证的标量综合
∂Ψ/∂θ        ≈  −[Ψ(lat+ε) − Ψ(lat−ε)] / (2ε)      # Richardson 外推
(1/sinθ)∂Ψ/∂λ ≈  [Ψ(lon+ε) − Ψ(lon−ε)] / (2ε·cosφ)
```

实测（nmax=10、随机系数、5 个点、ε=1e-4）：

| 分量 | 相对误差 |
| --- | --- |
| ∂/∂θ | **1.99e-10** |
| (1/sinθ)·∂/∂λ | **6.45e-10** |

> 这条铁律的价值：它会**当场抓住**"多除/少除一个 sinθ"这类错误。
> 我在推导阶段就写错了一次（东分量多乘了 1/sinθ），方向检验（对整体缩放不敏感）完全看不出来，
> 是这条差分铁律把它抓出来的。**所以它必须是 P 级验收项，不能只做方向检验。**

### 3.5 ✅ 已实测：点质量载荷的物理检验

构造一个正的 EWH 高斯鼓包（中心 30°N/100°E，σ=300 km，峰值 1 m），
经 `analysis(field_unit='ewh')` 得位系数，再算三维位移：

| 检验项 | 实测结果 | 物理预期 | 判定 |
| --- | --- | --- | --- |
| 载荷中心径向位移 | **−0.0236 m** | 正载荷 → 地表下沉（负） | ✅ |
| 24 点环（距载荷 4°）的 `cos(位移方向, 指向载荷方向)` | 均值 **+0.99982**，最小 **+0.99959** | 正载荷 → 水平位移**指向载荷**（辐合） | ✅ |
| 10 个散点的 `cos` | 均值 **+0.99913** | 同上 | ✅ |
| `\|u_h\|/\|u_r\|` | 0.18 – 0.61 | $\sim n\,l'_n/h'_n$ 量级 | ✅ |

**这组检验是水平形变实现的"物理锚"**：它同时钉死了 (a) 递推正确、(b) 符号约定正确、
(c) $l'_n/(1+k'_n)$ 用对了地方。验收测试直接照抄这 3 条。

### 3.6 ⚠️ 水平形变的三个数字特征（必须逐阶，不能近似成常数）

实测 SHKit 随包的载荷勒夫数表（`data/load_love_numbers.npz`，PREM-LLN，Wang et al. 2012）：

| n | h′ₙ | l′ₙ | k′ₙ | R·l′ₙ/(1+k′ₙ) [m] |
| --- | --- | --- | --- | --- |
| 1 | −0.28567 | +0.10358 | +0.02617 | 6.438e+05 |
| 2 | −0.99080 | +0.02329 | −0.30516 | 2.138e+05 |
| 3 | −1.04996 | +0.06989 | −0.19586 | 5.544e+05 |
| 10 | −1.42235 | +0.02827 | −0.06893 | 1.937e+05 |
| 40 | — | — | — | 1.182e+05 |

- **`R·l′ₙ/(1+k′ₙ)` 在 n=1..40 上跨 5.45 倍**（n=1..60 上跨 7.2 倍）→ 与 `Aₙ`（EWH）一样**是逐阶因子**，
  既不能当常数、也不能与 EWH/径向形变系数混用；
- **`l′ₙ` 不是单调的**：`l′₁=0.10358`、`l′₂=0.02329`、`l′₃=0.06989` —— 2 阶有个凹陷。
  任何"用 2 阶代表整体"的近似都会错；
- **`l′₀ = 0`**，且水平梯度**天然抹掉 0 阶**（常数的梯度为零）→ 见 §3.8。

### 3.7 极点与 `1/sinθ`（设计决定 —— 采用"递推求导"方案）

初版方案是"对 $1/\sin\theta$ 取单侧极限 + 定标 ε"。**SHSynth 方案 §4.9.2 给了更好的做法，
v2.0 采用后者**，因为它把极点特判**缩小到只剩一个地方**：

**① `dP̄/dθ`：把递推关系两边对 θ 求导，全程不出现 `1/sinθ`**

`legendre_columns` 的递推以 $t=\cos\theta$ 为自变量（$dt/d\theta=-\sin\theta$），
把每条递推两边对 $\theta$ 求导，就得到 $\mathrm d\bar P_{nm}/\mathrm d\theta$ 的**同阶递推** ——
**极点天然安全，无需任何特判**。这是它优于我初版方案的地方。

**② `P̄/sinθ`：只在极点行用解析极限覆盖**

只剩东分量需要 $\bar P_{nm}/\sin\theta$：

| 量 | 极点行为 | 处理 |
| --- | --- | --- |
| $\bar P_{nm}/\sin\theta$，$m=1$ | **有限且非 0**（$Q_{11}=\sqrt3=1.7320508076$） | 用同一条 $m=1$ 递推在 $t=\pm1$ 求值（$Q_{n1}$ 是 $\cos\theta$ 的 $n-1$ 次多项式） |
| $\bar P_{nm}/\sin\theta$，$m\ge2$ | **恰为 0**（$\bar P_{nm}\propto\sin^m\theta$） | 极点行置 0（这是**精确**的，不是近似） |

> ⚠️ **三种必须避免的错法**（都要进回归测试）：
> 1. **把极点写成 0** —— 会打掉一个有限值。实测：纯 $C_{11}$ 场在极点 $u_E=-1.7320508$，
>    不是 0；
> 2. **把极点写成 NaN** —— 整张图报废；
> 3. 给水平乘上 $(2n+1)/3$ 或 $\bar\rho/\rho_w$ —— 立刻差 $10^7$ 倍（与径向量级一比就露馅）。

**③ 我的 ε 标定保留为"验证手段"**（不是主实现）：如果用除法在极点求值，
误差随 ε 呈线性截断、并随 ε 减小转为相消主导，实测：

| ε（度） | 分母 sinθ | 相对误差 |
| --- | --- | --- |
| 1e-5 | 1.7e-7 | 1.7e-6 |
| **1e-6** | **1.7e-8** | **≈2e-7**（最优） |
| 1e-8 | 1.7e-10 | 5.5e-6（**相消主导，反而变差 27 倍**） |

⇒ 这条数字的用途是**反例回归**：`Q` 的极点值必须与"ε 单侧极限（ε=1e-6°）"吻合到 ~1e-7，
且必须断言 **ε=1e-8° 反而更差**（防止将来有人"顺手把 ε 调小"）。

**④ 诚实标注**：$u_N/u_E$ 在极点本身是**坐标奇异的**（极点的"东/北"依赖参考经线）。
照常给数、照常有限，但报告与 GUI 都加一句
*"极点行的水平分量依赖参考经线，跨极比较时请避开极点；极点不画矢量箭头"*；
而 **`magnitude = hypot(u_N,u_E)` 是旋转不变量，极点同样有效**，可以直接用。

> **已知局限（写进 README）**：$|\varphi|>89.9^\circ$ 的水平分量数值可用，
> 但应视为沿网格自身经线的极限值，不具"跨经线可比"的含义。

### 3.8 反推问题：水平形变**不能**当输入

SHKit 的框架是"正变换由「输入是」决定"。对水平形变：

- 水平梯度算子**抹掉 0 阶**（常数的梯度恒为 0）；
- 对 $n\ge1$ 它是**单射**（球面上"精确部分"的 Hodge 分解唯一）；
- 所以由 $(u_N,u_E)$ 反推位系数**只到差一个常数** $C_{00}$。

**v2.0 的策略（与现有"`h′₀=0`，径向形变不能反推 0 阶"同风格）**：

```python
analysis(..., field_unit="horizontal_displacement")   # → 明确 IndexError/ValueError
# 报错文案：水平形变是位系数的球面梯度，反推只能到差一个常数 C00；
#          若要反推，请用 field_unit="radial_displacement"（径向），
#          或显式提供 c00= 约束与水平形变的两个分量。
```

即：**水平形变只作为「输出为」的一档**，不作为「输入是」；若将来要做反演，另立 `invert_horizontal()` 并强制要求 `c00=`。

### 3.9 接口草案

```python
# ── basis.py / engine 扩展（与 legendre_columns 并列，内存策略相同：只留 3 列）────
def legendre_columns_vec(lat_deg, nmax) -> Iterator[tuple[int, ndarray, ndarray, ndarray]]:
    """逐列产出 (m, P̄ 块, dP̄/dθ 块, P̄/sinθ 块)。
       * dP̄/dθ: 把 legendre_columns 的每条递推两边对 θ 求导 → 全程无 1/sinθ，极点安全；
       * P̄/sinθ: 同列直接除 sinθ，**只在极点行**用解析极限覆盖
                 (m=1 → q_at_pole_m1；m≥2 → 恰为 0)。"""

def q_at_pole_m1(nmax, t_pole) -> np.ndarray:
    """m=1 时 Q_n1 = P̄_n1/sinθ 在极点的精确值：同一条 m=1 递推，
       种子 Q_11 = √3，在 t = ±1 处求值（Q_n1 是 cosθ 的 n−1 次多项式）。"""

# ── 新模块 shkit/gradient.py ─────────────────────────────────────────────
def sph_gradient(lat_deg, lon_deg, C, S, nmax=None, *,
                 chunk=None) -> tuple[np.ndarray, np.ndarray]:
    """标量球谐场的球面梯度：返回 (d/dθ, (1/sinθ)d/dλ)，形状同 synthesis()。
       4π 归一化、无 CS 相位；按 m 流式。"""

# ── synthesis.py 扩展 ────────────────────────────────────────────────────
def synthesis_horizontal(lat_deg, lon_deg, coeffs, *,
                         want=("north", "east"),
                         weights_scale=1.0, chunk=None) -> dict[str, np.ndarray]:
    """系数 → {"north": u_N, "east": u_E, 可选 "magnitude"/"azimuth"}，单位米。
       内部 = sph_gradient ∘ (逐阶 × R·l′ₙ/(1+k′ₙ))。
       与 synthesis() 一样支持 3D 系数 → 每个分量 (npoints, ntime)（多时间免费获得）。
       一次调用**同时**算北+东（不重复解析几何/不重复算递推）—— 见 §3.12 代价。"""

# ── units.py 扩展（与 SHSynth 的命名保持一致）────────────────────────────
FIELD_UNITS += ("horizontal_displacement",)          # 矢量：一个量，不是 east/north 两个量
FIELD_UNIT_LABELS["horizontal_displacement"] = "水平形变 u_h"
UNITS_NEEDING_LOVE_L = ("horizontal_displacement",)  # 原来只有 K / H，新增 L
_FORMULAS["horizontal_displacement"] = "R·l′ₙ/(1+k′ₙ)  (北/东分量由球面梯度给出)"
# 由 horizontal_displacement 换回标量场 → 报错（矢量、丢分量不可逆）
```

**三个设计决定（都跟随 SHSynth 的成熟结论）**：

1. **`horizontal_displacement` 是"一个矢量量"，不是 `east_/north_` 两个量。**
   与现有 `radial_displacement` 的命名风格一致；北/东是**分量**，不是独立的物理量。
2. **`SHCoeffs` 不需要任何新字段** —— 矢量性体现在**综合算子与产品层**，不在容器。
3. **高斯平滑照旧只施加一次，不新增参数名 —— 但理由要改对。**
   ⚠️ B1 实测更正：**不能**说"$W_n$ 与 $\nabla_H$ 可交换"。球面上 $\nabla_H$ 把阶 $\ell$
   混到 $\ell\pm1$，而空间高斯是逐阶乘子 $W_\ell$，两者**不交换**
   （实测 800 km 高斯下两种顺序的比值 $u_N$ **1.2355**、$u_E$ **0.9057**，差 24%/9%）。
   正确做法：平滑施加在**系数**上（与径向共用同一个 `gaussian_km`，只一次），
   水平形变是**那个已平滑标量场的梯度**；并让 `synthesis_horizontal` **不接受**
   `gaussian_km` 参数，从接口上杜绝二次施加与顺序歧义。

**关键设计：水平形变与多时间天然兼容。** `legendre_columns_vec` 与 `legendre_columns`
共用同一条列循环，把尾轴当 ntime 直接广播即可 ——
**"一个历元的水平形变"与"N 个历元的水平形变"是同一段代码**，v2.0 两大支柱在实现上是同一件事的两面。

### 3.11 水平形变的代价（实测，决定要不要"北+东一次算"）

同几何同批量，**一次调用同时算北+东**（不重复解析几何、不重复算递推）：

| 项（1° 全球，nmax=60，ntime=24） | 耗时 | 倍数 |
| --- | --- | --- |
| 径向（1 个分量，复用 `synthesize`） | 1.99 s | 1.0× |
| 水平（北+东，2 个分量，含导数递推） | 5.99 s | **2.2~3.0×** |

多出来的开销三块，都可解释：① `dP̄/dθ` 递推使勒让德部分浮点量翻倍；
② `P̄/sinθ` 一次逐元素除法；③ 每个 `m` 从 1 次矩阵乘变成 4 次（北/东 × cos/sin）。

> ⚠️ **实现必须流式，不许 materialize 全矩阵。** 实测：把 `P̄/sinθ` 用
> `legendre_pbar` 全矩阵实现（看着更"直观"的写法）会额外吃 **1 GB** 内存、
> 代价飙到 **4.81×**；改成与 `P`/`dP` 同一条列循环后降到 **2.2~3.0×**。
> 峰值内存约 `9·(nmax+1)·npoints`（`m`、`m−1`、`m−2` 三阶 × `P`/`dP`/`Q` 三套）。

### 4.2 直接移植：中文路径兜底（m2py 已解决，SHKit 必修）

`m2py/nc_viewer_pyside6.py:92-117` 的做法（同作者代码，可直接移植其**思路**，重写进 `io.py`）：

```python
_temp_dirs = []

def _open_nc_dataset(filepath, mode="r"):
    """netCDF4 / HDF5 的 C 库在 Windows 上打不开非 ASCII 路径；退化为 ASCII 临时副本。"""
    try:
        return nc.Dataset(filepath, mode)
    except (FileNotFoundError, OSError):
        if os.path.exists(filepath):                 # ← 关键：文件在，是路径编码的问题
            tmp_dir = tempfile.mkdtemp(prefix="shkit_nc_")
            _temp_dirs.append(tmp_dir)
            tmp_path = os.path.join(tmp_dir, "data" + (os.path.splitext(filepath)[1] or ".nc"))
            shutil.copy2(filepath, tmp_path)
            return nc.Dataset(tmp_path, mode)
        raise

@atexit.register
def _cleanup_temp_dirs():
    for d in _temp_dirs:
        shutil.rmtree(d, ignore_errors=True)
```

**SHKit 侧的三点差异**：

1. SHKit 用 `xarray.open_dataset`（底层也是 netCDF4）→ 兜底要包在 `xr.open_dataset` 外面，
   并同样覆盖 `netCDF4` 直接调用的路径（`_read_grid_netcdf` / `_read_grid_netcdf_var`
   和 GUI 的变量列表 `main_window.py`）；
2. ⚠️ **写入也会失败，而且 `m2py` 的方案没有覆盖这一半。** 本机实测：
   netCDF4 **创建**一个非 ASCII 路径下的文件同样失败，但报的是
   **`PermissionError`（误导性极强，不是 `PermissionError` 该有的原因）**。
   ⇒ 写入的兜底方向相反：**先写到 ASCII 临时文件，再 `shutil.move` 到位**。
   `m2py` 的 `except (FileNotFoundError, OSError)` 恰好也能接住 `PermissionError`
   （它是 `OSError` 子类），但只读路径够用、写路径不够；
3. 临时目录要用 `try/finally` + `atexit` **双保险**（长批量跑时目录不能泄漏）；
   大文件（1°×257 历元的 nc ≈ 130 MB）拷贝有成本，**只在首次失败时才拷**；
   读路径必须 **eager `.load()`**（临时副本要在返回前删掉，懒句柄会悬空），
   并在 `attrs` 里记 `shkit_path_workaround` 让用户看得见。

> ✅ **本项（A0.5）已实施**：`shkit.io.open_nc_dataset()` / `to_netcdf_path()` / `_write_nc()`，
> 4 处调用点全部改掉。修复前 `tests/run_all.py` 是 **228/231**（`grid nc` 与两个 CLI nc 写出全挂），
> 修复后 **231/231**。见 `io.py` 顶部 "Windows / Chinese paths" 一节。

> 修法三条，都不是放宽判据：①把探针任务做成**秒级长任务**（~200 历元批量分析），
> 让子进程有足够长的存活窗口；②`terminate()` 之后 `join()` 并确认**真的死了**
> （`killed` 为真才算数，否则重试并打印 `crashed` 内容）；③给
> `SubprocessRunner._handle` 加防御分支：队列里出现非 `(kind, body)` 的消息时
> **必须发 `failed`**，否则异常逃出 `run()`、QThread 静默结束，父进程既收不到成功也
> 收不到失败 —— 那正是最难查的一类故障（界面一直等着，什么提示都没有）。
> 验证：`run_all.py test_gui_smoke` 连跑 4 次 **133/133**（连全量跑也绿）。

> ⚠️ **E 阶段最后一步（真的去出安装程序）当场抓到一个发版级事故**：

> | 检查（同一个场按 m 与按 cm 各走一遍） | 实测 |

> | 系数之比 `C(cm)/C(m)` | **恒等于 100**（91 个非零系数，13 位内） |

> **不需要任何换算**。软件从不需要知道单位。
>
> 真正与单位有关的只有**绝对物理标注**：打印出来的 `m`/`mm`、以及"真实 GRACE 应在
> mm 级"这类按 SI 写的量级自检 —— 文件若是 cm，这些数字要按 cm 读（÷100 才是米）。
> 现在摘要与形变页的提示改成了这个说法（"线性、无需换算；只有绝对标注要按文件单位读"），
> 并新增 `validate_units.t_unit_scale_is_linear`（5 项）把上表逐条钉住。
> ⚠️ 另一个实现细节仍然成立：判断依据必须是**用户声明的那一档** —— 正变换一做完，
> 系数与报告里的 `field_unit` 都会变成 `geopotential`，那时"这串数原本是 cm 还是 m"
> 只留在运行分析时记下的值里。

> **教训（第三次同源）**：这四条全部落在**"算得对"与"看得对"之间**。
> 前半段的判据（批量≡逐历元、FFT≡直接法、系数域≡网格域）一条都没漏，
> 但它们**全都在数值层**；只要画布上的经度、周期、海岸线、历元这四件事没被断言过，
> 全绿照样能让用户看到一张错位的图。

### 5.7 第五个报障：**第一次**打开 mascon 必报 `NetCDF: Not a valid ID`

| --- | --- | --- |
| 第一次打开那份 mascon 必报 `RuntimeError: NetCDF: Not a valid ID`，之后再开就好 | GUI 为了填「变量」下拉框，在读数据的 `LoadWorker` **之外又开了一次同一个文件**。netCDF4/HDF5 的 C 库是**进程级全局状态**，两个线程同时 open 同一份文件就会这样炸；而且这个异常是 `RuntimeError`，**不是** `OSError` —— `open_nc_dataset` 里"非 ASCII 路径就退到临时副本"的兜底只 `except OSError`，**根本兜不住它**。又因为这条路径每次打开都会走两遍、只是竞态窗口很窄，所以表现为"第一次必错、重试能过" | ① 变量名单改由**同一次读取**带出（`meta['nc_variables']`，只列真正含 lat/lon 维的网格变量），GUI 不再开第二次文件；② `open_nc_dataset` 全程过一把模块级 `RLock`，并认 `(OSError, RuntimeError)`、临时副本读取**重试 3 次**；③ 顺手修掉"指定变量读"的两个老问题：以前先自动探测再按变量读**读两遍**（112 MB 文件 = 两次复制），而且那条路的 meta 是**最小版**——用户在下拉框里换个变量就丢时间轴与变量单位；现在两条路共用 `_nc_var_meta()` |

> 这里第三方的报错类型（`RuntimeError`）与直觉（IO 错误 → `OSError`）不一致，

### 5.8 载入那份 mascon 要 10 多秒（性能，实测定位）

用户报「载入 mascon `.nc` 很慢，大概 10 多秒」。**先量再改**，逐阶段实测（112 MB /
720×1440×256 = 265 M 个值，路径在中文目录下）：

| 阶段 | 实测 | 处理 |
| --- | --- | --- |
| 复制到 ASCII 临时目录（非 ASCII 兜底） | **0.06 s** | 不是瓶颈（原以为它是） |
| `xr.open_dataset + ds.load()` 读 1 GB float32 | **4.5 s** | 这是"必须读的数据量"，只能靠少读（见下） |
| 整块 float32 → float64 | 0.9 s + 一倍内存 | 大数组**保留文件原精度**（`_KEEP_DTYPE_MIN = 2e7`，并在提示里写明）；这一步曾被 `read_grid` 末尾那句 `np.asarray(..., dtype=float)` 抵消，一并修掉 |
| `summary()` 的统计（`isfinite` + `nanmin/max` + `v**2` 的均值） | **3.4 s** | 先改成**沿时间分块累加**（临时数组只有一块）并**缓存**；§5.9 又按用户要求把口径改成**逐时次**，这一项直接消失 |
| 界面在载入时调 `summary()` **两次**（左侧摘要 + 报告占位） | 2 × 3.4 s | 缓存后第二次 0 s |

结果：载入端到端 **约 10–11 s → 3.7 s**，峰值内存 2.12 GB → 1.06 GB（+ 一块临时数组），
统计量与整块计算**逐值一致**（回归里有断言），`summary()` 第二次调用 < 1 ms。
（这 3.7 s 是"整块读"这一档的数字；§5.9 的懒加载把**首屏**进一步降到 0.61 s。）

> 剩下的 ~3 s 全是"把 1.06 GB 全读进来"本身（256 个历元 × 1 M 个点）。
> 要再快只剩一个方向：**懒加载**（打开时只读第 1 个历元 + 轴，其余按需读，每次约 4 MB）——
> 首屏能到亚秒级，播放也更顺；代价是加载期间要保持文件句柄与临时副本存活。

### 5.9 懒加载 + 统计口径改为「按第 k 个时次」（用户第三轮要求）

用户接着问「**为什么 Panoply 载入和绘图都很快**」，并要求「统计那一行数值范围/RMS
要么改成按第 k 个时次」。两件事一起做，都先量再改。

**为什么 Panoply 快**：它只读 netCDF 的"目录"（维度/属性，**64 ms**）和**一个切片**
（4 MB，**253 ms**）就出图；SHKit 原来在打开时把 1.06 GB 全 `load()` 进来（**2.42 s**
把 256 个时次连读，或单层 253 ms）。所以差距不在"谁读得快"，而在"读多少"。

由此实现 `shkit.io.LazyTimeCube`（`read_grid(..., lazy_time=True)`，GUI 默认开）：

| 动作 | 实测（同一份 mascon） |
| --- | --- |
| 打开（只读第 1 个时次 + 轴 + 预分配 1.06 GB 缓冲） | **0.61 s**（整块读 **2.60 s**） |
| 按需取某一层 `ensure(t)` | 0.25 s（后台已补到时是 0 s，内存视图） |
| 后台按块补齐（`PREFETCH_BLOCK = 64`） | 3.9 s 走完 256 层（≈ 9.5 ms/层，不阻塞界面） |
| 补齐后与整块读 | **逐值一致（0 差异）** —— 省时间不以改数值为代价 |

界面侧（`shkit/gui/main_window.py`）：

* 载入后立刻可用（首层已在内存），状态栏显示「其余 N 个时次后台读取中…」，
  定时器轮询进度；补齐后自动把"要全部历元"的页面（时间序列）换成真实曲线；
* **需要全部历元才补齐**：批量分析（含独立进程那条路，要 pickle 整条序列）、
  趋势/周年场，进入前 `ensure_all_epochs(progress=…)` 并显示进度；时间序列页在补齐
  前只画占位并**明说**「后台补齐中」，绝不同步卡住界面；
* `Dataset` 对懒加载网格**不再展平**（`values is None`，`ntime` 从立方体来），
  取某一层走 `value_slice(t)`；换变量/重载/关窗都会 `close()` 掉旧句柄与 ASCII 临时副本。

**统计口径**：摘要里的「数值范围 / RMS」原先描述**整块**。对 256 个历元的 mascon，
整块求范围既贵（3.4 s，`v ** 2` 还要再开一份 2 GB 临时数组）又不对应用户正在看的
那一层。现在改成**逐时次**（`Dataset.stats(t)` / `summary(t)`，按 `t` 缓存），
并在行尾写明「（第 k/N 个时次）」，单时次数据退化为「（整块）」。切时次时左侧摘要
跟着刷新；实测第 1 层 −94.1 … 327.0、第 200 层 −1428 … 280.8 —— 整块口径会把这两个
完全不同的图压成一个数字。

回归：`test_io_roundtrip.py` 36 项（LazyTimeCube 按需/补齐/逐值一致/close 不泄漏/
单时次自动回退并写明理由）、`test_gui_smoke.py` 197 项（不展平、逐时次摘要与缓存、
后台补齐进度、补齐前不为占位读整块、close 交还句柄；**网格与散点两条统计路径都按

### 5.10 第六个报障：「显示」切到其他选项后，播放不生效 / 播的还是原始图

用户原话：**「SHKit v2.0 版本，显示 切换到其他选项，播放不能起效或者播放的是原始图」**。
§5.6 第 4 条当时以为已经修完了（"只有单历元结果时**明确提示**先去批量分析"），实际上
那个"明确提示"**从来没有落地**，另外两条更隐蔽的路也没堵。先复现、再修：

复现（离屏，24 个历元的小网格，逐帧比对"画布上的场到底是谁的"）：

| 场景 | 修前实测 |
| --- | --- |
| 载入后**不做分析**，把「显示」切到重建场/差值/输出场 | 标题写着「原始网格」—— 三张图画的都是**原始数据**，切了等于没切 |
| 只做过一次「运行分析」（解第 1 个历元），播放「重建场」 | 从头到尾 **\|场\|max 一模一样**（1 种取值），每一帧都是那一个历元的场 |
| 同上，看 `_epoch_extra` | 播放期间只补算出一个历元，且因为认错 worker，结果还记到别的历元名下 |

真因（三处，全在"算得对"与"看得对"之间）：

1. `_refresh_map()` 在 `recon is None` 时**静默**改画原始数据（`which == 0 or recon is None`
   走同一支），标题也写成"原始网格"——用户切了「显示」看到的是同一张图，正是"播放的是原始图"。
2. `_epoch_fields()` 没有多历元系数时**无条件**返回 `self.recon/self.outfield`。那是
   「运行分析」那一次解的**某一个**历元（`AnalysisWorker.time_index`），却被当成"任何历元
   的重建场"。§5.6 修的是"批量系数存在时按历元重算"，这条单历元分支一直没修。
3. 换时次会触发**按需补算**（后台线程），但播放定时器**不等它**：一帧 250 ms、一次补算
   0.3 s 起，于是每一帧画的都是那个旧场。另外 `_on_epoch_analysis_done` 用
   `self._epoch_worker.time_index` 认历元，而"队列投递"与"`isRunning()` 转 False"之间有
   窗口 —— worker 可能已被下一次补算替换，A 历元的结果会记到 B 历元名下。

修法（`shkit/gui/main_window.py`）：

* **记住 `self.recon` 属于哪个历元**（`_single_t`），`_epoch_fields()` 改为返回
  `(重建场, 输出场, 是否真属于这个历元)`；不是这个历元就返回"没有"，交给上层去补算
  或如实提示 —— 这样"别人的场"从数据上就拿不到了；
* **不撒谎**：地图上方新增一行提示（`map_note`），逐历元视图写明"当前显示 X · 第 k/N 个
  历元 · 来源"；拿不到这个历元的场时：已有系数 → 启动按需补算并写明"正在补算第 k 个历元"
  （画布上若上一张**也是**逐历元图就先留着，避免拖动时闪白），一个系数都没有 → 占位图
  直接写"先运行分析 / 批量分析"，**绝不**画原始数据冒充；
* **播放等帧**：`_play_step()` 只有在下一历元的场真的就绪时才前进，等待期间提示行给出
  "已等 n 秒"；等太久（`PLAY_WAIT_SECONDS_MAX = 300 s`，按**墙钟**计，与帧率无关）或补算
  失败就停下并给出建议（去批量分析），不会一直空转；
* `_on_epoch_analysis_done/_failed` 改用 `self.sender()` 认历元；并顺手堵上"**上一个数据集**
  的补算/批量分析结果落进当前数据"这条路（`worker.dataset is not self.dataset` → 丢弃），
  否则换了数据后画布/逐历元表会画别人的东西；
* 同类三处一起修：① `_coeffs_for_epoch()`（水平形变页）不再拿单历元系数顶替别的历元，没有
  就显示"第 k 个历元还没有系数（正在按需补算）"；② 系数统计页的"重建残差 RMS"只在该历元
  真有系数时才报，并写明是第几个历元；③ **逐时次导出**在只有单历元结果时**拒绝**（原来会把
  同一个场写给每个历元 —— 一份看起来正常、其实全错的序列），**导出 GIF** 逐帧等待该历元的
  场（否则 GIF 是同一帧复制 n 份）。

回归：`test_gui_smoke.py` **+8 项**（换数据后没有系数时切「重建场」不留原始数据、明确提示
先分析、`_single_t` 记对、第 1 个历元上单历元结果算数、播放逐历元走到窗口末端、**每一帧都
等于它自己那个历元的重建场**、末帧 ≠ 第 1 个历元的场、逐时次导出在单历元结果下拒绝写出），
该套 **197 → 205 项**，全套 **19 套 1040 项全绿**（`python tests/run_all.py`）。

> **教训（第四次同源）**：这四条又全部落在**"算得对"与"看得对"之间**。§5.6 已经写下
> "只有单历元结果时**明确提示**"，但**没有人把这句话变成一条断言**，于是它只活在文档里；
> 而同一段代码里"没有结果就画原始数据"这条兜底，看起来像"至少给用户看点什么"，
> 实际效果是**让用户以为自己看到的是重建场** —— 在科学软件里，这种"体面的兜底"
> 比直接报错更坏。

### 5.11 「运行分析」改成一次解完全部历元 + 逐历元系数落盘缓存（用户第二轮要求）

§5.10 交付后用户追问：**「逻辑上，点击运行分析，应该载入全部数据并处理完全部数据，
缓存到本地。绘图时就直接展示即可。为什么导出 GIF 时提示说都需要重算？」** —— 他说得对。
§5.10 的修法只是"把每次重算**如实说出来**"，但根子在于界面把"解一个历元"和"解所有历元"
拆成了两个按钮，而**绘图与导出需要的恰恰是后者**：

| 事实（改动前） | 说明 |
| --- | --- |
| 「运行分析」只解**当前那一个**历元 | `AnalysisWorker(time_index=滑块)`；诊断报告/逐阶谱本来就是"一个解" |
| "全部历元"挂在另一个按钮上 | `analyze_series`（「逐历元诊断 → 批量分析」），权重与法方程只组装一次 |
| 而没有磁盘缓存 | 系数只在内存：逐历元补算留最近 6 个、重建场留最近 4 个 |
| 于是逐历元视图/GIF 只能**逐个历元补算** | 每次都是一次完整 `analysis`，正是用户看到的"都要重算" |

改动（用户选定 A+B，并要求导出时"自动先补齐、不打断"）：

* **A：多时次数据的「运行分析」= 一次解完整条序列**（内部走 `analyze_series`，仍是子进程
  优先/线程回退那套）。`self.coeffs` 变成"当前历元那一解"的切片，诊断报告/逐阶谱/系数
  统计/导出系数都跟着时次走（报告页给出"整条序列的共享诊断 + 当前历元那一行"）。
  「切时次」从"触发一次求解"变成**纯切片**；「批量分析」按钮保留，是同一个求解的另一入口。
* **B：逐历元系数落盘缓存**（新增 `shkit/gui/coeff_cache.py`）：写在数据文件旁边
  （`<名>.shkit-coeffs.npz`，不可写时退到用户缓存目录并写明）。键 = 源文件
  `路径/大小/mtime_ns/变量/点数/历元数` + **全部影响系数的参数**（nmax、积分元规则、
  估计方法、迭代次数、tau、归一化、正则、alpha、正则幂、**高斯平滑半径**、输入/输出
  物理量）+ 缓存格式版本。任一项不同即未命中（重算并覆盖，**一个数据集只留最新一套**）；
  载入数据时先查缓存，命中就直接读，并在状态栏与「逐历元诊断」页写明"这是缓存"。
* **导出不再逐帧求解**：GIF 与逐时次导出在开始前先 `_ensure_series_sync()`（一次、带进度、
  可取消）把整条序列解完，之后每帧只是 `synthesis`。逐时次导出因此**取消了** §5.10 的"拒绝"
  —— 它现在能给出每个历元**自己**的场（回归里直接比对两个历元写出的文件内容不同）。
* **删掉"逐历元按需补算"整条机制**（`_epoch_single/_epoch_extra/_epoch_worker/`
  `_pending_epoch/_ensure_epoch_coeffs`）：一次解完整条序列与"解一个历元"几乎同价
  （固定成本主导，每历元边际 1.4 ms），逐个补算既慢又难解释，属于纯粹的历史包袱。

> ⚠️ 顺手抓到一个**真 bug**：`analyze_series` **从来没有** `gaussian_km` 参数 ——
> GUI 的「高斯平滑」只作用于「运行分析」（单历元），「批量分析」静默忽略它。也就是说
> 文档里"批量分析与逐时次各点一次运行分析**逐位相同**"这句话，在半径非 0 时是**假的**。

> **批量（含平滑）≡ 逐历元 analysis + apply_gaussian，逐值 ≤1e-12**，以及"平滑 = 逐阶
> 乘 W（C00 不变、nmax 阶被压低 W(nmax) 倍）"。

回归：`test_gui_smoke.py` **205 → 214 项**（多时次「运行分析」一次解完 + 表格同一次填满；
换时次只是切片、没有新求解；没有系数时切视图开跑整条序列且不画原始数据；缓存写盘 /

### 5.12 打包：安装路径带空格（用户要求「打包时检查」）

用户的要求是：**「打包的时候，注意检查如果安装路径存在空格的情况，导致无法正常运行的问题」**。
先量后改，结论分两半：

**① 运行期本身对空格是安全的（先证明，再决定要不要改代码）**

| 试的东西 | 实测 |
| --- | --- |
| netCDF4/HDF5 写/读**带空格**（还带中文）的路径 | 逐值一致（`max|Δ| = 0`） |
| 懒加载 `LazyTimeCube` 走带空格路径 | 逐值一致 |
| `TEMP` 本身带空格（用户名带空格就会这样）时的非 ASCII 兜底副本 | 写读正常、逐值一致 |
| `shkit/` 里有没有把路径拼进命令字符串 | **没有**：无 `shell=True`/`os.system`/`os.popen`；唯一的子进程走 `multiprocessing` spawn（参数按列表传，Windows 由 `list2cmdline` 负责加引号） |

关键结论：**危险的不是路径里有空格，而是"把路径拼进命令字符串"**。所以审计的重点
从"文件路径"转到"进程与脚本"。

**② 真会坏的地方（找到一处）**

`packaging/build_installer.ps1` 的静默安装：
`Start-Process $Setup -ArgumentList "/DIR=$TestDir"` —— `-ArgumentList` 是**按空格拆分**
的，只要验证目录名（或 `-BuildRoot`）里带空格，`/DIR` 的值就会被拆成两个参数，于是
"装到错误的目录"或直接失败。改成 `/DIR=`"$TestDir`"`，并且**验证目录名故意带空格**
（`_install test 带空格`），装完先断言 `<那个目录>\SHKit.exe` 真的存在。

**③ 把它变成打包流程的硬性步骤（不是"记得手动试一次"）**

* 新增 **3/4 步**：把整个目录包复制到 `<构建根>\dist space 带空格\SHKit`，从那里再跑
  一遍 `SHKit.exe --self-test`；
* `-VerifyInstall` 把安装程序静默装到**带空格**的目录再跑一遍自检；
* 这两处都要求冻结版自检里**特定三步必须出现 PASS**（带空格 nc 往返 / 带空格缓存命中 /
  独立子进程），少一项就红。

冻结版自检从 9 项加到 **12 项**：新增「带空格路径：网格 nc 写→读逐值一致」、
「带空格路径：逐历元系数缓存写→读命中」、「独立子进程能起来并返回结果」。
最后那一步是打包后最容易坏的功能（D12 的崩溃隔离：spawn 要**重新拉起自己**，
路径里的空格 + `freeze_support()` 时机 + 队列，任何一处不对就变成"子进程异常退出"）。
自检还会打印 `sys.executable` 是否含空格，日志里一眼能看出装在哪。

**实测（真的跑了一遍打包，构建根就用带空格的 `D:\SHKit build 空格测试`）**

| 环节 | 结果 |
| --- | --- |
| 目录包自检（`<构建根>\dist\SHKit`） | **12/12，exit=0** |
| 复制到 `dist space 带空格\SHKit` 后自检 | **12/12，exit=0**，日志里 `含空格=True` |
| Inno Setup | `SHKit_Setup_v2.0.exe`，92 MB |
| 静默安装到 `_install test 带空格` → 自检 | **12/12，exit=0** → 卸载并清理 |

回归：`test_io_roundtrip.py` **36 → 40 项**（带空格路径的 nc 往返 / 懒加载 / 系数与 grd
导出读回 / `TEMP` 也带空格时的非 ASCII 兜底）、`validate_v2.py` **82 → 90 项**
（`/DIR` 必须整体加引号、验证目录名必须带空格、必须把目录包复制到带空格路径再自检、

> **教训**：在文档里写"支持带空格路径"没有用 —— 必须让**打包脚本自己**把整个包搬到

### 5.13 水平形变改成按需计算 + 本页自己的色标；顺带查清「60 阶场看起来偏低」

用户一次报了三件事，前两件是界面行为，第三件是数值质疑。

**① 「水平形变应该点击计算后再算。不要运行时都计算了。」**

改前：`_apply_series`（运行分析 / 批量分析完成）与 `_on_time_changed`（换时次、播放的
每一帧）都会 `_refresh_horizontal(force=True)`；切到该页签也会顺手算。网格上一次全球
梯度综合实测 **1.08 s**（720×1440 / nmax=60），而播放时**每换一帧**都要重来一次 ——
用户说的"运行时都计算了"就是这个。

改后：只有点「计算水平形变」才算。其余场合只把旧图**作废**并写明：

* 新增系数版本号 `_coeff_version` 与图指纹 `_horiz_sig = (_coeff_version, id(dataset), t)`；
* `_mark_horizontal_stale(why)` 把画布换成"……点「计算水平形变」重算"的占位（全篇不撒谎）；
* 「海岸线」开关改成**只重画**（用上次算好的 `north/east`），不再重算。

**② 「水平分量与地图里共用了色标，画不出来。」**

`HorizontalCanvas` 以前拿的是**地图页那一个** `ColorScale`（D1 的"一个面板驱动所有地图"）。
一旦地图那边是手动 vmin/vmax（例如 EWH 的 ±700 cm），毫米级的 `u_N/u_E` 就被压成一片
颜色 —— 看起来就是"画不出来"。现在本页有自己的 `ColorScale`：按形变数据自动定 2–98%、
两个分量对称于 0（仍然**互相**共用，保证可横向比较），水平模从 0 起。
"应用色标"按钮的作用范围也在工具提示与说明书里写清了：**地图页与趋势页**，不含本页。

**③ 「现在重建的 60 阶场，有点不像 60 阶，信号泄露偏低很多」——查完结论：不是 bug**

在这份真实数据（CSR RL0603 mascon，720×1440×256，**纬度是单元中心** −89.875…89.875，
`nlon = 2·nlat` 所以 auto 选 `dh`）上逐条量过：

| 检查 | 实测 |
| --- | --- |
| 带限场闭环（在**这份网格自己的经纬度**上综合 nmax=60 的场再解回来） | 系数相对误差 **3.7e-16**，`gram max\|K−I\|` ≈ **1.5e-15** |
| 直接解 60 阶 vs「240 阶解截断到 60 阶」 | `max\|ΔC\| = 1.0e-28`，重建场相对差 **5.5e-18** —— 逐值相同 |
| `longitude_fft='auto'`(FFT) vs `'direct'` | 系数相对差 **2.2e-15** |
| `rule='dh'` vs `'grid'` | 重建 RMS 比 0.7845 vs 0.7845（同一答案） |
| 逐阶解的重建 RMS/输入 RMS | 20 阶 0.536 → 40 阶 0.681 → **60 阶 0.785** → 80 阶 0.841 → 120 阶 0.904 → 240 阶 0.948 |

也就是说：SHKit 的 60 阶解**就是**"真·截断投影"，没有任何压低/漏乘/多乘；少掉的
21.5% RMS（约 38% 的方差）**真的在 60 阶以上** —— 这份 mascon 的空间分辨率是 0.25°
（~28 km），而 60 阶的半波长约 333 km。要保住更多细节就得提高 nmax（120 阶 → 0.90，
240 阶 → 0.95），或者接受"这是 60 阶该有的样子"。

回归：`validate_core.py` 新增 `t_truncation_is_exact`（**+5 项**）：单元中心 + dh 的权重
仍归一、宽带场的 gram 接近单位、**解到 L ≡ 高阶解截断到 L**、重建 RMS 随阶数单调上升，
外加一条反向对照（多乘一次 300 km 高斯会明显压低，说明前一条有区分度）。
`test_gui_smoke.py` **+5 项**（分析后不自动算 / 切页签不算 / 点按钮才算 / 换时次只作废 /
分量不被地图手动色标压平），色标那条断言从"共用"改成"各有各的"。全套 **19 套 1090 项全绿**。

> **教训**：两条界面问题都是"贴心"贴错了地方 —— 自动计算把一页很贵的图绑在每一次
> 播放上，共享色标把一页的量级绑在另一页的手动设置上。判断依据是**代价与语义**：
> 贵的、逐历元的量应该由用户点名再算；不同量纲的图不该共用一根色标。

### 5.14 图上少两样、多一样：白箭头、去掉国界；散点的多时次查清并补齐

用户这一轮提了三件事（前两件是"图上不要什么/要什么"，第三件是询问能力边界）。

**① 水平模里的箭头与左下角比例尺文字改成白色**

`HorizontalCanvas._maps` 原来 `quiver(color="0.1")`（近黑）+ 比例尺文字默认深色。现在
箭头 `facecolor="white"` 并带一层很细的深色描边（`edgecolor="0.15", linewidth=0.25`），
比例尺文字 `labelcolor="white"` 再叠 `patheffects.withStroke(0.15)` —— 纯白落在 viridis
的亮黄端会看不清，描边把两头都照顾到（用户要的是白色，这里只是让它同时可读）。

**② 地图不再画国界**

`MapCanvas._finish` 原来一次画两层：`coastline`（实线）＋ `borders`（虚线）。现在只画
海岸线。`borders_110m.npz` **仍在包里**（`load_coastlines("borders")` 还能用，测试也还在
校验它的飞线修复），只是地图上不再画；说明书的"海岸线开关"与打包清单里都写明了这一点。

**③ 「散点支持多时间吗」——支持，但补了三处**

查清后的答案是：**支持**，`values` 就是 `(N, ntime)`，地图/播放/导出与网格走同一条
（时间行、一次解完全部历元、逐帧真播）。文件形式四种：矩阵 `.npy (N,2+ntime)`、
宽表 `value,value1,…`、宽表**列名即日期**、宽表任意列名配 `val_col=[…]`。
顺手补掉几处缺口：

| 缺口 | 原来 | 现在 |
| --- | --- | --- |
| 任意列名的多列选择 | `val_col=["e2002","e2003"]` 直接 `TypeError: list`；提示语还写着"如需多个时次请用 val_col=" | `val_col` 接受**序列**（列名或序号），并校验它没指到经/纬度列 |
| 日期轴 | 散点永远只有历元序号（趋势/周年页因此拒绝拟合） | **数值列名能当日期用**（`2002-01-18` / `2002-01` / `2002`，且严格递增）就自动落进 `meta['time']` → `Dataset.time_axis()` 有日期；解析不出**不编造** |
| 长表被悄悄读错 | 一行一个「点×历元」+ 日期列的长表会被当宽表，**只取第一列**，用户拿着半份数据都不知道 | 坐标大量重复（>40%）时给出**明确警告**："这看起来是长表……请先透视成宽表" |
| 逐时次导出格式 | 默认 `.nc`（散点写不了），点了只得到"0 个文件" | 载入时按数据种类设默认（网格 `.nc`／散点 `.csv`）；真选了不匹配的格式就改成 `.csv` 并**说明** |
| 载入即开工 | "显示"停在重建场时，新数据一打开就在后台解整条序列（懒加载的文件还会被整块读进来）——用户没点过任何按钮 | 新增 `_loading` 守卫：**载入期间不自动开跑**，只提示"点「运行分析」"；用户显式切视图/点按钮才算 |

回归：`test_io_roundtrip.py` **40 → 50 项**（四种写法往返、`val_col` 列名/序号、日/月/年
列名当时间轴、非日期列名不编造、长表告警）、`test_gui_smoke.py` **219 → 228 项**
（地图无虚线只有海岸线、白箭头+白文字、散点多时间的时间行/一次解完/逐帧真播/导出 csv
两历元不同、载入不自动开工）。全套 **19 套 1109 项全绿**。

> **教训（与 §5.13 同源）**：能力边界要**先量后答**。"散点支持多时间吗"这句话背后是
> 四条不同的读写路径，其中两条（任意列名、日期轴）只差二十行代码，却是"能不能用"的
> 区别；而最危险的不是不支持，是**长表被当成宽表悄悄读了一半** —— 所以宁可吵一点也要警告。

### 5.15 两个追问：进度条卡在 0；缓存会不会无限涨

用户这一轮问了两句话，两句都问在点子上 —— 第一句是真 bug，第二句我们本来就**没管住**。

**① 「如果本地有缓存，运行后，进度条会卡在 0 不动」**

先量后改，量出来的事实（离屏跑真实窗口，打印 `value/visible/label`）：

| 时刻 | value | visible | label |
| --- | --- | --- | --- |
| **新开窗口（什么都没载入）** | 0 | **True** | `''` |
| 载入数据后 | 0 | True | `''` |
| 首次真算（序列线程） | 0 → 163 → 1000 | 跑完 False | 完成 |
| **新窗口 + 缓存命中** | **0** | **True** | `''` |
| 单历元跑完 | 1000 | **True**（永不隐藏） | 完成 |

真因很朴素：`QProgressBar` **一塞进布局就是可见的**（`setVisible(False)` 从来没写过），
而唯一的隐藏动作挂在 `_on_series_finished` 上 —— 那是"序列线程跑完"的出口。缓存命中
在 `_start_series` 里**提前 return**（不跑线程），于是那根 0% 的条永远留在界面上；
"单历元分析完成"干脆把一根 100% 的条永久留下。用户看到的就是"点了运行，进度条卡在 0"。

修法：进度条**出厂即隐藏**，并让每个出口都走同一个收工函数 `_progress_idle()`：
缓存命中（`_mark_cache_hit_progress()`：推到 100% + 写明"直接读本地缓存（本次未重算）"）、
单历元成功/失败/取消、换数据集（`_stop_workers_for_reload`）。单历元那条路的
`finished` 也接到收工上 —— `finished` 无论如何都会发，不会漏。

**①-b 在真实 mascon 上再量一遍，才发现"卡在 0"还有第二层**

上面那几条是拿合成小数据量的，修完在**用户那份真实 mascon**（1 036 800 点 × 256 历元，
旁边躺着 7.38 MB 缓存）上重跑，把时间线打出来，才看清真正扎眼的东西 —— 进度条在
**前 5 秒**是这样的：

| 时刻 | 界面 |
| --- | --- |
| 0 – 3.0 s | **进度条根本没出现**：`_ensure_all_values` 在补齐全历元（1 GB）＋构造 payload，全发生在 `setVisible(True)` **之前**，界面只是在发呆 |
| 3.0 – 4.85 s | 进度条出现，**可见、0%、标签空白**：1 GB 数据正在 pickle 进子进程管道 |
| 4.85 – 6.1 s | **仍是 0%**，标签 `批量求解 1–256/256`（子进程已收到、还没吐第一个阶进度） |
| 6.1 s 起 | 才开始走（19 → 90 → … → 1000），25.9 s 全部算完并隐藏 |

也就是说：**"缓存命中不隐藏"和"真算时前 5 秒没有任何可信进度"是两件事，用户看到的是
同一个症状。** 修法：

* 把 `_progress_busy(label)`（`setRange(0, 0)` 的**忙碌条**）提前到补数**之前**；
  `_lazy_progress` 顺手把 `3/256…` 写进条形文字；
* 交给子进程那一步也先摆忙碌条：`正在把 256 个历元的数据交给独立进程（约 1037 MB）…`
  —— 有没有百分比是客观事实，没有就给"在干活但不知道多久"，而不是一根死 0%；
* `on_progress` 收到第一个真实百分比时自动 `setRange(0, 1000)` 切回百分比条，
  `_progress_idle` 收工时也还原量程。

**①-c 而且那句缓存提示在撒谎**

同一份数据里发现：旁边那份 7.38 MB 缓存的**键里写的是旧路径**（`D:\myds\…`，文件现在
在 `D:\华为家庭存储\…`），**根本命不中** —— 可我刚加的 `cache_hint` 是按"文件在不在"
写的，于是它写着"本地已有该数据的缓存（7.38 MB）——「运行分析」直接读它，不重算"。
这正是最不能接受的那种撒谎。加 `coeff_cache.probe(dataset, params)`（只比键、不解压
数组），提示与「本地缓存…」都改成按**能不能命中**说话，对不上就直说"对不上 → 会重算并
覆盖它"。

**①-d 根因：键里不该有绝对路径（顺手修掉，CACHE_VERSION 2 → 3）**

顺着上面那条查下去，模块 docstring 一直写着"写在数据文件旁边，把数据一起拷走缓存也
跟着走"，但 `cache_key` 里有 `os.path.abspath(path)` —— **拷走必然命不中**，用户那份
缓存就是这么废掉的（他自己把数据从 `D:\myds` 搬到了 NAS 路径）。改成
`size + mtime_ns + 前 64 KB 的 sha1 + kind + npoints + ntime + variable`：

* 拷贝（`copy2`／同步盘／资源管理器）保留 mtime_ns、内容不变 → **命中**；
* 内容改了（size / mtime / 开头字节 变）→ **不命中**；
* 同一个文件搬到别处 → **命中**，不再白算一遍；用户缓存目录那份文件名也跟着变得可搬。

路径改为写进 payload 的 `source_path`（**只用于诊断**，不参与匹配）。这是键语义变更，
所以 `CACHE_VERSION` 提到 3、旧缓存一律自动未命中并重写一次（用户那份 7.38 MB 会在下次
求解时被同路径的新缓存覆盖）。

**①-e 用户第二轮：「缓存了，但是我点运行，还是重跑了一遍」「识别到缓存时，输入是 这个应该自动切换吧」**

先查证据（不猜）：mascon 旁边那份缓存的 mtime 是 **17:58:43**、`cache_version=3` ——
说明用户跑的确实是新代码，**不是**"没装上新版本"。再看键：

| | 「输入是」 | nmax |
| --- | --- | --- |
| 缓存里记的（他上次跑用的） | **`ewh`** | 60 |
| 重开界面载入后的默认值 | **`geopotential`** | 60 |

两句话拼起来就是全部真相：`field_unit`（「输入是」）**是键的一部分**（同一块网格声明成
geoid / EWH / geopotential 除的 `f_u` 不同，**系数真的不一样**，所以它必须在键里），
而界面的默认「输入是」与缓存里的不同 → 必然未命中 → 重算；重算又把缓存写成"当前这套"，
下次打开默认值还是对不上 —— **来回打转**（他的文件里已经留下两次重算的痕迹）。
所以他提的「识别到缓存时，「输入是」应该自动切换」正是唯一正确的修法。

修法：`coeff_cache.find_any(dataset)` 按"文件指纹相同、**参数可以不同**"找出这份数据的
缓存（数据旁边那份优先，否则取用户缓存目录里最新的），界面在**载入时**据此调用
`_adopt_cached_params()` 把参数切回缓存那一套，再读一次缓存：

* 「输入是」/「输出为」/ nmax / 积分元规则 / 估计方法 / 迭代 / tau / 归一化 / 正则 /
  alpha / 高斯半径**一起切**（只切「输入是」照样对不上）；
* 控件里没有那个取值 → **跳过并写明**"这些取值当前界面没有、未切"，不静默；
* 缓存退在**用户缓存目录**里（数据目录只读 —— NAS 只读挂载就是这样）也照样认得出来：
  `find_any` 会扫那个目录里每一份 `key` 按文件指纹匹配，不依赖文件名/路径；
* 状态栏写明"这份数据有本地缓存（写于…：输入是=ewh、nmax=60…）—— 已把参数切回缓存
  那一套并直接读它，本次没有重算"；同一句话也进**常驻**的 `cache_hint`（状态栏那句很快
  会被懒加载后台进度顶掉，实测过）；
* **语义边界**：自动切回只发生在**载入**时。用户改完参数点「运行分析」是另一个语义
  —— 那是他要的新参数，必须按新参数重算并覆盖缓存，**不回退**。这两条都写进了回归。

实测（用户那份 mascon）：载入前 `输入是=geopotential` → 载入后 `输入是=ewh`、nmax=60、
逐项与缓存一致 → **载入即命中**（不再重算），点「运行分析」0.71 s 返回、进度条写明
"本次未重算"。

回归见本节末尾的计数与条目说明。

**①-f 用户第三轮：「有缓存时，点击运行分析弹出提示，用户决定是否重跑」**

上一轮的修法（载入时静默把参数切回缓存那套并直接命中）解决的是"打转"，但**读没读缓存
这件事用户看不见**：点了「运行分析」，界面一闪就有结果了，他不知道读的是缓存还是刚算的。
所以他要求把决定权交回来 —— 有缓存就先问一句。

修法：`_start_series(..., ask_cache=True)`，只有**用户显式点**「运行分析 / 批量分析」时
才问；`_ask_series_cache()` 弹一个三选一的对话框（返回 `'cache' / 'recompute' / 'cancel'`）：

```
标题：本地已有缓存
这份数据已经有一份本地缓存（数据文件旁边，7.4 MB，写于 2026-09-14 17:58:43）：
　参数：输入是=ewh、nmax=60、积分元=dh、估计方法=quadrature
　与当前界面参数一致。
　当前内存里的结果：就是这份缓存读回来的（本次会话还没有重算过）。
直接读缓存最快；重新计算会按当前参数解一遍整条序列，并把缓存覆盖成新的。
［直接读缓存（不重算）］（默认）　［重新计算（覆盖缓存）］　［取消］
```

* **默认按钮是"读缓存"**：用户的历史报障就是"明明有缓存还重算"，所以不该默认重算。
* 三个出口都验过效果：读缓存 → 不跑求解、进度条写"本次未重算"；重算 → 真的解一遍并
  **覆盖**缓存文件（`_series_cache` 变回 None）；取消 → 缓存不读、也不重算，内存里那份
  结果逐值不变，状态栏写明"已取消"。
* **不问的两类情况**（这是设计边界，都写进了回归）：① 参数与缓存**不一致**（用户刚改过
  ——他要的就是新参数，问了反而烦）；② **自动补算**的路径（导出 GIF/逐时次导出/切视图）
  —— 那里插一个模态框会把人卡住，`ask_cache` 默认 False，只有显式按钮传 True。
* 测试上：模态框在离屏套件里会**永久阻塞**，所以默认把 `_ask_series_cache` 换成"读缓存"
  并计数，另用 `QMessageBox` 子类（把 `exec` 换成"自动点某个按钮"）验证**真实**的
  按钮→决定映射，以及"关掉对话框（没点按钮）当取消"。

**② 「缓存会无限量吗？」—— 会（其中一半），现在不会了**

| 位置 | 原来的增长性 | 现在 |
| --- | --- | --- |
| 数据文件旁边 `<name>.shkit-coeffs.npz` | **一个数据集一份**（改参数覆盖同一个文件）。实测 mascon nmax=60/256 历元 = **7.04 MB**；合成 nmax=120/256 = 58 MB（噪声系数压不动，7.04 MB 那份是真实场光滑才压得小） | 加**单份上限 256 MiB**：超过就**不写盘**并在状态栏说明（不在用户数据盘上悄悄放几个 GB） |
| `%LOCALAPPDATA%\SHKit\cache`（数据目录不可写时的退路） | 按"数据集 × 参数"散列，**每换一组参数多一份，永远不清理** → 真正无界 | 加**总量上限 512 MiB**：每次写盘后按最久未用（mtime）修剪到 80%，并写明"删了几份、释放多少" |

再加一个入口让用户自己看得见、自己动手：**文件 → 「本地缓存…」**（`show_cache_manager`）
显示当前数据那份缓存的大小/时间、用户缓存目录的份数/总量/上限，两个按钮就地清理
（删当前数据的缓存 / 清空用户缓存目录），并说明"删掉不影响已经算出来的结果"。
参数面板底部常驻一行 `cache_hint` 报占用（并如实说明能不能命中）—— 用户不用猜。

**③ 顺带抓到的：`spawn_available()` 在一个危险组合上判错了**

写复现脚本时踩到：脚本没有 `if __name__ == "__main__"` 保护，而界面默认把求解放进
`spawn` 子进程 → **子进程把整个探针脚本又跑了一遍**（输出整段重复、多开一个窗口，
还因为递归起子进程把自己挂死）。原来那个检查只在脚本里出现 `"__main__"` 字符串、
又没写保护时才拒绝 —— "既没保护、也没提 `__main__`"的脚本被判为可用。独立实验坐实了
后果：标记文件里 **2 个进程各 1 行**（带保护则只有 1 行）。

判据现在按 CPython 的真实规则来（`multiprocessing.get_preparation_data`）：
`.exe` 启动器 / 冻结包**不会**把主模块交给子进程（`__file__` 以 `.exe` 结尾就直接放行），
`python -m <pkg>` 按模块名导入也无副作用，只有"普通 `.py` 主模块 + 没有 `if __name__`
保护"才拒绝，并说清楚后果。回归：`validate_v2.py` 加一条**运行时**断言（临时写一个
无保护脚本、真起子进程、要求返回 `NO` + 原因）。

回归与本轮计数：`test_gui_smoke.py` **228 → 258 项**（进度条四处出口、忙碌条→百分比条
切换、缓存提示、单份上限、修剪、清空、菜单项、`probe()` 能命中/不能命中、**拷贝到别的
目录仍命中**、内容变了不命中、**载入时自动切回缓存参数并命中**、**改完参数点运行必须
按新参数重算**、**有缓存时点运行必弹提示**（按钮→决定的映射、三种决定的实际效果、
自动补算路径不问））、`validate_v2.py` **90 → 91 项**（无保护宿主脚本必须被拒）。
全套 **19 套 1140 项全绿**（当轮）。

> **教训（第三次同源，见 §5.13 / §5.14）**：
> ① 用户问"会不会无限涨"时，答案不能是"设计上每个数据集一份"—— 那只描述了**数据旁边**
> 那一半；另一半（用户缓存目录）确实是数据集×参数、只增不减。**"有界"必须逐个位置量
> 清楚，并且要有上限、有清理、有用户看得见的入口**，三者缺一都还叫无界。
> ② `QProgressBar` 这种"控件默认可见"的坑，只要隐藏动作挂在**某一个**出口上，就一定
> 会在别的出口漏出来；而"卡在 0"这种报障，**合成小数据量不出来**，必须在用户那份真实
> 数据上把时间线打出来才看得见（前 5 秒里，3 秒是"根本没显示"、2 秒是"显示了但没有
> 百分比"）。
> ③ **"文件存在"不是"能用"**：缓存键里的绝对路径让"拷走缓存跟着走"这句承诺在实现上
> 是假的，界面还照着"存在"去报"直接读它、不重算"。凡是界面替用户下结论的地方，判据都
> 必须是**真正决定行为**的那个条件（这里是键的比对），不是它的近似（文件在不在）。
> ④ **"缓存不命中"要分清是"用户改了参数"还是"默认值≠缓存"**。前者重算天经地义；后者
> 是个**死循环**（默认值对不上 → 重算 → 缓存被改写成默认那套 → 下次打开还是对不上），
> 用户看到的只是"明明缓存了、点运行还是重算"。区分办法是问一句"这份数据**有没有**缓存"
> （不看参数），有就把界面参数切回它那套并说明；用户改完参数**点运行**则是另一个语义，
> 必须按新参数算 —— 两条语义都要有回归守着。

### 5.16 「为什么水平场是单独的，径向形变可以输出？」——量清楚之后：挪出界面线程 + 加导出

用户这一轮是**提问**（不是报障），但问题问到了设计的不对称处。照"先量后答"办：

**① 先答"为什么"（三条，都有实测撑腰）**

径向形变 $u_r$ **本身就是标量场**：它和重建场/输出场是同一类对象 —— 同一套系数 ×
逐阶因子的一次综合（重建场 $f_u$、输出场 $f_t$、径向形变 $R\,h'_n/(1+k'_n)$）。代码上
就是 `synthesis(target_unit='radial_displacement')`，所以它天然继承「输出为」下拉、
`导出输出场`、播放/GIF/逐时次导出。

水平形变不一样，三条：

| # | 事实 |
| --- | --- |
| 1 | 它是**矢量场**（$u_N$、$u_E$ + 派生 $\|u_h\|$、方位角）——不是"一个标量层"，一个「显示」下拉项和一个色标装不下（§5.13 那个"共用色标画不出来"就是这么来的） |
| 2 | **算法不同**：位系数的**球面梯度**（$\partial/\partial\varphi$ 与 $\frac{1}{\cos\varphi}\partial/\partial\lambda$，带极点处理），用另一张勒夫数表 $l'_n$（径向用 $h'_n$） |
| 3 | 物理上**不可逆**：由 $(u_N,u_E)$ 反推位系数只到"差一个常数 $C_{00}$"，所以「输入是」里根本不列它（库里明确拒绝） |

**② 代价不对称（真实 mascon 网格 720×1440、nmax=60、同一份系数）**

| | 1 个历元 | 256 个历元 |
| --- | --- | --- |
| 标量场（重建/输出/径向） | 0.16 s（散点直算）/ 0.20 s（网格） | 9.2 s |
| 水平形变（规则网格，经度 FFT） | **0.08 s** | 24.2 s（N/E 各 (720,1440,256) ≈ **4.25 GB**） |
| 水平形变（散点直算） | **79.25 s**（510×） | 不可行 |

所以"点击才算 + 单独一页 + 自己的色标"是对的：界面**不能假定数据是规则网格**。用户那份
mascon 恰好是网格（0.08 s，很轻），但散点上"顺手算一下"完全不可接受。

**③ 顺带查出一个真问题：这一步以前是同步跑在界面线程里的**

`计算水平形变 → _refresh_horizontal → synthesis_horizontal(_grid)` 全在界面线程：散点上
**整窗冻住约 79 秒，没有进度、不能取消**；而且 `subproc.py` 里早就写好了
`horizontal_grid` 这个子进程任务（`JOB_KINDS` + `run_job` 分支），**界面从来没调用过它**
（死代码）。

**④ 用户选了 A（修冻结）+ B（加导出）**

**A. 挪出界面线程**（不改变"点击才算"与"单独色标"）：

* `gradient._accumulate` / `_gradient_grid_fft` 加 `progress` / `cancel`（按"点块 × 阶"报
  进度；取消抛 `RuntimeError("cancelled")`，与 `series` 同一约定）；两条路径都透传。
* 新增 `gradient.canonical_scaled(coeffs)`：单位检查/换算 + 逐阶因子。**界面进程算一次**，
  线程与子进程拿到**逐位相同**的输入 —— 子进程里只剩纯数值。
* `subproc` 的 `horizontal_grid` 分支接上 `progress`（并把 `path`/`reason` 带回界面，
  不静默换算法）；新增 `horizontal_points`（散点走 `horizontal_field`）。
* 新增 `workers.HorizontalWorker`（线程路径）与 `MainWindow._on_horiz_ready/_failed/
  _cancelled/_finished`；「停止」按钮与关窗/换数据都能停下它。
* 测试：点击**立刻返回**（实测 1 ms）且 worker 在跑、进度回呼到达、协作式取消立刻生效、
  子进程 ≡ 线程**逐值相同**（`max|Δu_N| = 0.00e+00`）、`path` 一致。

**B. 导出水平形变**（文件菜单两项）：每个历元写 **3 个文件**（`u_N`/`u_E`/`|u_h|`，单位 m）
—— 一个文件只装一个变量，任何工具都读得进去；网格 `.nc`、散点 `.csv`。复用 D10 那套
`ExportWorker` + `ExportDialog`（可暂停/继续/停止），并给它加了一个 `label_of`，好让进度条
如实写出"这个历元写了哪几个分量"。**散点上先给耗时估算**（1M 点 / nmax=60 → 79 s/历元，
256 历元约 5.6 小时）让用户决定，不默认开跑一晚上。

**⑤ 顺手修掉一条"绿得不对"的老测试**

改完 D12 那块，原本稳过的「子进程被强杀」用例开始失败：`crashed=['msg'] TypeError: times
必须是 shkit.timeaxis.TimeAxis`。查下来是**用例自己**的问题 —— 它给子进程的载荷里
`times=[str(x)[:10] …]`（字符串列表），而 `SHCoeffs.__post_init__` 只接受 `TimeAxis`，
于是子进程**一进去就抛异常**；这条用例以前"绿"是因为它碰巧在子进程走到那行之前就把它杀
了（纯竞态）。改成真的 `TimeAxis.from_datetimes(...)` 之后，它绿在**正确的原因**上：
`子进程异常退出（exitcode=-15）`。

**⑥ 本轮计数**：`test_gui_smoke.py` **228 → 272 项**、`validate_horizontal.py` **66 → 73 项**
（进度/取消/钩子不改数值）、`validate_v2.py` **91 项**。全套 **19 套 1161 项全绿**。

> **教训**：① "为什么 A 是这样、B 是那样"这类问题，答案要落到**代价与数学对象**上
> （标量 vs 矢量、逐阶乘法 vs 球面梯度、0.08 s vs 79 s），而不是"历史原因"；
> ② 一旦把某个重活标成"按需计算"，就要同时问一句"**它是不是还在界面线程里**" ——
> 按需只解决了"什么时候算"，没解决"算的时候窗口还活不活着"；
> ③ 死代码会掩盖问题：`subproc` 里躺着一条从没被调用的水平形变分支，等于那条"崩溃不拖垮
> 界面"的保护形同不存在。

### 5.17 v2.0.1 打包（版本号口径 + 打包前文档复核）

**① 版本号口径改了：补丁号进安装程序**

产物 `SHKit_Setup_v2.0.1.exe`；`validate_v2.py` 的两条版本断言也跟着改：

② `MyAppVersion` 必须与 `SHKIT_VERSION` **完全相同**（不再只比主次版本）。

**② 顺手修掉一处"补丁号把用户缓存全废掉"**

### 5.3 关键路径与并行

```
B0 ── B1 ──┬── B2 ───────────── M2   ← 完全独立，可与其他线并行
           ├── B3 ←────────────┐    （B3 依赖 A3，是唯一的两线交汇点）
           └── B4              │
A0 ──┬── A1 ── A2 ── A3 ───────┴──┬── D2 ── D3 ── M5/M6
     │                            │
A0.5 ┘   C1 ── C2 ────────────────┘
     └── D1
```

**B0 起步最早、且不依赖任何人** —— 它只依赖"公式已经钉死"（本项目已完成 H1–H14 的验证），
所以**第一天就能做**，做完立刻把契约固化，两条线再各自推进。

`B0–B2/B4`（水平形变）与 `A*/C*`（多时间）之间**只共享 `legendre_columns` 与 `A3` 的经度加速**，
接口在 A0 之前就已冻结 → **两条线可以平行推进**，这是 v2.0 能按期出的主要原因。
**唯一的交汇点是 B3**（水平形变也走 FFT），它必须等 A3 落地；若要并行，B3 可延到 M3 之后。

> **同一份冻结契约要同步给 SHSynth 侧**：F1–F11 与 golden fixture 是**两个包共用**的，
> SHSynth 的对应阶段也必须以 B0 的产出为输入。B0 因此是**跨两个项目的第一个交付物**，
> 建议由先开工的一方生成、另一方拷入并校验 `provenance`（版本 + 勒夫数表哈希）一致。

## 7. 与 m2py / m2csharp / SHSynth 的关系与许可

三个参考实现都是同作者代码，但**借用的层次完全不同**，必须分清：

| 来源 | 借什么 | 不借什么 |
| --- | --- | --- |
| **m2py / gridSHconvert** | 勒让德递推、DH 权重、高斯滤波系数、载荷勒夫数表（`README.md` §9 已声明） | 它的 **FFT 收尾索引**（整体平移一个经度格，见 §2.3）；它的 `fft↔fft 必须配对` 隐式约束 |
| **m2csharp** | 只作为 FFT 路径的**独立对表基准**（SHSynth 已用它定位出上述平移） | 同上（它是 m2py 的移植，**继承了同一个平移**）；不引入 .NET 运行时（纯 Python 只差约 2×） |
| **SHSynth** | ①**冻结的 `series_nc` / `.dat` 落盘契约**（§2.4）；②**递推求导 + `Q` 解析极限**的极点方案（§3.7）；③FFT 适用性判据与回退规则；④水平形变的单位命名与解析锚点 | 它的实现代码（两包必须能各自独立运行，不 import 对方） |

- **算法层**：水平梯度算子是在 SHKit 的 4π 约定下**独立推导并数值验证**的
  （H1–H14；`m2py` 的 `out_type=3` 至今是 `NotImplementedError`，**没有水平形变实现**）。
  两条独立推导路径（我方 vs SHSynth 方案 §4.9）在解析锚点上**互相印证**：
  纯 $C_{10}$ 与纯 $C_{11}$ 的 $u_N/u_E$ 都吻合到 2.2e-16，极点 $u_E=-1.7320508$ 也一致。
- **水平形变：两边各自实现（已定）**。既然是两份代码，一致性**不靠共享代码，靠 §2.5 的
  F1–F11 冻结约定 + golden fixture（`≤1e-12`，目标 `0.0`）**。三条纪律：
  1. **B0 先做**：fixture 在任一侧首次实现时就生成并冻结，不要等两边都写完再对；
  2. **勒夫数表要钉哈希**：两边的 `l′` 表若一个有 CE→CF 改正、一个没有，
     水平形变会整体偏几个百分点而**所有内部测试仍然全绿**（F2 + fixture 里的 `F^h_n` 向量就是防这个）；
  3. **跨包测试允许 skip**：对方不在时优雅跳过并打印原因，`run_all.py` 不能因此变红。
- **显示层**：只**借鉴交互与布局思路**（色标面板、双读数、数值表、逐时次导出、中文路径兜底），
  代码按 SHKit 的 PySide6 + matplotlib 结构重写；
  SHKit 继续**刻意不使用** GPL-only 的 Qt Charts / Qt Data Visualization，保持闭源商用可行。
- **许可结论**：v2.0 **不新增任何第三方依赖**（FFT 用 `numpy.fft` / `scipy.fft`，已在依赖内）。
  `docs/许可与闭源商用说明.md` 补一句："水平梯度算子为本项目新增；FFT 经度路径、
  递推求导极点方案与落盘契约参考同作者的 SHSynth 方案；显示交互参考 gridSHconvert。"
